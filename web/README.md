# DuckLink core in the browser

Runs the same `ducklink_core.wasm` wasip2 component that `ducklink` runs
under `wasmtime`, in a browser — via wasm-cm's portable **runtime-guest**
driver. No jco transpile, no wasi-polyfill `RuntimeBindgen`.

## Architecture

- **JS bindings** — generated by
  [`wit-js-bindgen --role runtime-guest`](https://github.com/tegmentum/wit-js-bindgen)
  from the built `ducklink_core.wasm` binary. The emitted file inlines
  the wasm-cm tagged byte-frame codec (25 tags) and exports two entry
  points: `registerHostProviders(driver, impls)` (host imports) and
  `bindRuntimeGuest(driver, instanceHandle)` (exports). See
  `generate.sh` — bindings are derived from the wasm binary, NOT from
  the WIT source tree, because the WIT tree has drifted ahead of the
  built wasm on prior landings and driving bindings from the wasm keeps
  import names in lockstep.
- **Runtime-guest driver** —
  [`@tegmentum/wasmos-browser`](https://github.com/tegmentum/wit-js-bindgen/tree/main/examples/wasmos-browser)
  boots `wasmcm_runtime_guest.wasm` (a portable wasm-cm interpreter core
  module) and hands back a driver speaking the runtime-guest C-ABI
  (`parseComponent` / `registerHostProvider` / `registerRouter` /
  `instantiateWithImports` / `callExport`).
- **WASI provider bridge** — `@wasmos/runtime-guest-bridge` (from
  elena-wasm) adapts `@tegmentum/wasi-polyfill`'s per-interface plugin
  implementations onto the byte-frame provider protocol
  `registerHostProviders` expects. `createStandardPolyfill` builds a
  polyfill with the standard cli/filesystem/io/clocks/random plugin
  bundle; `createWasiProviders` returns the interface-keyed impls for
  hand-off to the bindings' `registerHostProviders`.
- **duckdb:\* + tvm:memory imports** — stubbed for the plain-query
  path. Extension loading + TVM spill are separate lanes not yet
  ported to the runtime-guest driver (see "Follow-ups" below).

This is the same shape elena-wasm's `@wasmos/dataset-ducklink` uses
(the W1c commit in that repo's `docs/vela-wasmos-browser-runtime.md`
plan doc — this landing is the W6 follow-up).

## Why we retired jco + wasi-polyfill's `RuntimeBindgen`

- `RuntimeBindgen` transitively depended on jco's `js-component-bindgen`
  to unbundle the wasip2 component into core modules, which failed on
  the current `ducklink_core.wasm` build with `exception refs not
  supported without the exception handling feature` — see the previous
  README's "Known blocker" section (removed in this landing).
- The wasm-cm runtime-guest is a portable component-model interpreter
  that does its own unbundling internally. No jco pass, no exception-
  refs failure, and the same `.wasm` binary runs identically under
  wasmtime (native) and the browser runtime-guest.
- The runtime-guest byte-frame codec is a strict superset of DuckLink's
  type surface. Elena-wasm's codec-gap investigation
  (`docs/investigations/runtime-guest-codec-vs-ducklink.md` in that
  repo) verified this — 25 tags implemented, 22 exercised, no gaps.

## Files

- `bindings-runtime-guest/` — `wit-js-bindgen --role runtime-guest`
  output. Regenerate with `npm run generate`. Do not hand-edit.
- `generate.sh` — thin wrapper around the `wit-js-bindgen` binary.
  Reads `WIT_JS_BINDGEN` (path to the binary) and
  `DUCKLINK_CORE_WASM` (path to the wasm; defaults to
  `public/ducklink_core.wasm`).
- `run-core.mjs` — `instantiateCore(componentBytes, additionalImpls?)`
  boots the driver, wires host providers, parses + instantiates the
  component, and returns the bound `duckdb:component/database`
  interface. `runQuery(bytes, sql)` is the one-shot helper.
- `browser-entry.mjs` + `index.html` — the primary smoke: fetch the
  core wasm, run a query, paint the result.
- `verify.mjs` — headless Chromium driver over `index.html`. Reports
  `ok` / `error` / `timeout` + the rendered `<pre>` contents.

## Setup

The two runtime deps are sibling checkouts, wired as `file:` links from
`package.json`. The setup expected today is:

- `../../wit-js-bindgen` — clone of https://github.com/tegmentum/wit-js-bindgen,
  built (`cargo build --release`).
- `../../elena-wasm` — clone of https://github.com/tegmentum/elena-wasm,
  with `packages/runtime-guest-bridge` built (`pnpm -r build`).

Then:

```bash
npm install
npm run copy-wasm       # stage ducklink_core.wasm into public/
npm run generate        # regenerate bindings against the staged wasm
```

## Run it

```bash
npm run dev             # vite dev server; open the URL, watch <pre>
npm run verify          # headless Chromium: instantiates + runs a query
```

Expected `verify` output on success:

```
=== RESULT status: ok ===
columns: answer, two
rows: [[{"tag":"int64","val":"42n"},{"tag":"int64","val":"2n"}]]
```

## Regenerate bindings

```bash
npm run generate
```

Overrides:

- `WIT_JS_BINDGEN=/other/path/wit-js-bindgen npm run generate`
- `DUCKLINK_CORE_WASM=/absolute/path.wasm npm run generate`

## Follow-ups (not in this landing)

The pre-existing entry points that ride `wasi-polyfill` directly —
`extension-host.mjs`, `tvm-host.mjs`, `browser-ext-entry.mjs`,
`browser-tvm-entry.mjs`, `browser-prepared-entry.mjs`,
`browser-corpus-entry.mjs`, `browser-cron-entry.mjs`,
`browser-aba-entry.mjs`, `aot-tvm-test.mjs`, `corpus-verify.mjs` — are
NOT ported to the runtime-guest driver here. They referenced the old
`configurePolyfill` / `duckdbStubImports` / `hostProviderStubs` helpers
that this landing removed from `run-core.mjs`, and the wasi-polyfill /
jco deps they need are no longer declared. They still exist on disk;
follow-up landings would need to:

1. Rewire `extension-host.mjs` to register per-interface impls into
   `registerHostProviders` instead of assembling a jco-style `Imports`
   record (and use the runtime-guest driver's export surface for the
   extension component's own boot).
2. Rewire `tvm-host.mjs` similarly for the spill path — the WIT
   contract is unchanged, only the import wiring differs.
3. Re-add the removed `verify-*` scripts to `package.json` once each
   entry point boots on the runtime-guest lane.

Cross-repo counterpart lives in elena-wasm's plan doc rows W2 (host-
component) and W3 (sdk) — the same rewire pattern applied to each
consumer.

## Consuming DuckLink from other JS packages

Elena-wasm's `@wasmos/dataset-ducklink` package is the canonical
integration path — a browser-side `@wasmos/dataset` provider whose
`createDuckLinkDataset({ corePath?, sqlSeed?, ... })` returns a
`Dataset` handle backed by this exact `ducklink_core.wasm`. It uses
the identical runtime-guest boot pattern (same `wasmos-browser` +
`runtime-guest-bridge` + `wit-js-bindgen --role runtime-guest`
bindings), so keeping DuckLink's own browser smoke on the same stack
mechanically enforces that both consumers exercise the same code path.

See `wasmos/README.md` (in this repo) for the full integration story.
